# Notification navigation

Notification clicks use the existing scope navigator and timeline locator. `HostNotification.scope` captures the producing window's credential-free `homeId`, `scopeId`, `serverHomeId`, and `connectionRef`; `route` carries the session, optional agent, and optional `turn` or `interaction` query. Session-list observations without an exact agent or frame do not invent one. Merged notifications open `/activity` in the captured scope.

`NavScopeBoundary` is the only click consumer. It verifies explicit destinations even in the active scope, preserves the dirty-draft confirmation and source visit, and shows the existing scope recovery surface for missing or changed targets. Missing explicit notifications are not treated as deleted back-stack entries. Active connections are validated without rebinding the session or reopening a remote connection. Preparation waits for a cancelled predecessor's rollback before starting the next scope change.

On desktop (`apps/kiki-desktop/src/main/notificationService.ts`), Electron's native `Notification` bridge registers the configured application identifier (`com.kiki.desktop`) on Windows so toasts and click callbacks remain owned by Kiki rather than a generic shell process. Neither banner timeout nor app focus alone acknowledges an unviewed conversation; `click` events focus the matching space window and emit the typed navigation payload to the renderer.

`HostNotification.sessionIds` and `scope` bind native entries to conversations. `useViewedSession` acknowledges the viewed session, including its child-agent routes, only while visible and focused. Merged entries remain until all their sessions are acknowledged. Each in-flight GUI send has a `deliveryId` and records the sessions actually viewed during that send. After sending completes, compensation acknowledges only that delivery, even if the user has since left its conversation; newer episodes and other scopes remain unread. Scope changes invalidate old focus probes, and notification switches are checked again after a pending probe returns.

`apps/kiki-desktop/src/main/notificationService.ts` persists active notification metadata in `notification-registry.json` under the desktop instance's user-data directory, independently of the Kiki home, with atomic JSON replacement so acknowledged sessions reconcile cleanly across restarts without clearing unrelated scopes.

Each click has a monotonic `navigationId`; navigation acknowledgment clears only that id, independently of conversation acknowledgment. The desktop preload adapter (`window.__KIKI_ELECTRON__` / `src/host/tauri.ts`) registers its live listener before draining pending clicks and discards duplicate or older deliveries. Cold page boot serializes the captured scope into Router state and verifies before mounting the target. Activation callbacks require the desktop process to remain running; reopening a page is not a test of activation after the entire desktop process exits.

The claim-matched fixtures are `src/host/{tauri,browser}.test.ts` and `src/lib/{awayNotify,useAwayNotifications,navScope,navReading}.test.ts(x)` in `apps/kiki-gui`, plus `apps/kiki-desktop/test/windowAndTrayLifecycle.test.ts` and `apps/kiki-desktop/test/securityAndIpc.test.ts`. `node apps/kiki-gui/scripts/visual-proof-completion-notification.mjs` walks the real GUI with a mocked native bridge: click routing, focus-gated acknowledgment, other-session retention and reconnect/reopen deduplication. It does not exercise an OS click.

# Work modes and document preview

Work modes add a window-local entry and view to an existing Kiki space. They do not create another session authority or change an existing session's profile, model, permissions, runtime, or workspace binding. The mode entry is available by default; explicit `KIKI_EXPERIMENTAL_WORK_PRESETS=false` or `[experimental] work_presets = false` still disables it. Availability does not install packages or prerequisites.

## Space and window ownership

`GET /api/work-presets` reads the active server's home. Preferences and enabled/removed mode state use `IAtomicDocumentStore` under `work-presets/modes`. The built-in Kiki mode remains available. Work enablement explicitly previews, consents to, installs and enables the Office, Writing, Extract and optional Table checks packages. Failed packages are reported while successful items are retained for a retry. Reading, customizing, disabling or removing a mode never installs or re-enables a package. Removing Work retains shared packages, sessions and files.

`KIKI_WORK_PLUGIN_ROOT` is a development source override containing directories named `kiki-office`, `kiki-writing`, `kiki-extract` and `kiki-work`. Without it, background mode reads use bundled catalog metadata without a network request. Explicit enablement reads the user's configured marketplace or the published default catalog; an unavailable catalog reports a retryable failure instead of silently substituting bundled sources. An unpublished Table checks package remains unavailable. Ordinary manual marketplace browsing retains its existing published-catalog and bundled-metadata behavior.

Desktop `--home <path> --preset <id>` selects one space × mode window identity. `desktop_window_mode` exposes `{presetId, windowId}` and `open_mode_window` launches a peer window without writing home settings. Native window IDs use a `w-` prefix, which the GUI's window ID validator accepts.

Desktop discovery shares one in-flight result per native window and the home-local `server/ensure.lock` PID lease used by CLI `serve --ensure`. The native leader starts one foreground sidecar directly and retains its process until authenticated readiness, then attaches to it as an externally owned shared service. Cancellation or window exit stops only a pre-ready child; closing a window does not stop a ready shared daemon. Passive `waiting` events update progress only. Local socket loss drives GUI recovery; SSH/remote windows refresh their retained local-control connection without changing the active selection.

Explicit desktop restart/update uses `/api/desktop-lifecycle`, whose canonical schemas live in `packages/protocol/src/rest/desktop-lifecycle.ts`. Only a service marked `desktop_managed` by desktop bootstrap can be stopped; the consent names its current `server_id`. Native confirmation states that all windows in the affected space disconnect and unfinished work will be cancelled and drained. Unconfirmed work keeps running. Confirmed work goes through the existing `start.ts` close path, session lifecycle `close`, agent removal, task cancellation and persistence drain; activity is not a permanent prohibition. The service blocks new mutations while draining. When normal shutdown closes HTTP before session teardown finishes, `serve --ensure` also waits for the registered live instance to release or exit before spawning a replacement. A still-live unreachable instance produces a recoverable reason at the wait deadline, not a second daemon. Native waits for the old registry instance to disappear without force-killing it, then startup uses the same home-local PID lease. A drain exceeding 90 seconds returns a recoverable reason instead of killing the process. Updates retain `server/ensure.lock` until installation finishes (or until the owning process exits); CLI ensure does not steal a live owner's lock after a time threshold, and reports a still-running update after its own bounded wait. Another home has a separate lock and is not restarted by a one-space restart. External services retain their original ownership guard.

## Preview contract and recovery

The canonical request and response schemas live in `packages/protocol/src/rest/document-preview.ts`. The server registers `POST /api/sessions/{session_id}/document-preview` and session-scoped `GET .../document-preview/assets/{asset_id}`. Workspace sources retain runtime/filesystem authorization; session-media sources retain their session binding. Remote files are read through their runtime before local rendering. GUI consumers must fetch `ready.assets[].url` through the authenticated connection, not substitute a host filesystem read.

- **PDF:** use browser PDF.js when no Poppler renderer is present. Bundle its worker, CJK CMaps and standard fonts; do not depend on a locally installed executable for the basic PDF path. Poppler can render PNG pages when present but is not a main-package dependency.
- **DOCX, XLSX and PPTX:** use the pinned OfficeCLI renderer from the `kiki-office` plugin. Missing rendering capability returns `install-prerequisite` recovery for `kiki-office/officecli` with `plugin_state` set to `not-installed`, `disabled` or `enabled`. Preview requests never install or enable a plugin. A missing plugin uses the existing single-plugin install plan, fingerprint and explicit consent; a disabled plugin uses a clearly labelled enable action; an enabled plugin needs only its prerequisite installer. These recovery actions do not call Work enablement or change removed mode state. XLSX navigation reports worksheet names and accepts a selected sheet/range. An unspecified range with a selected sheet requests a bounded `A1:Z50` viewport; consumers can request other ranges.
- **Text and CSV:** return source fidelity with offset, bytes and truncation facts. Continue by offset; do not present a bounded window as the whole file.
- **Legacy Office, ODF and unknown formats:** return `unsupported` with `download-original` recovery. `.doc/.xls/.ppt/.odt/.ods/.odp` do not currently have an integrated high-fidelity renderer. A future LibreOffice adapter belongs in a separately consented heavy plugin, not a silent main-package download.

Page input is a positive integer, with no permanent 100- or 1000-page cap. Existence/count is supplied by the actual renderer. Assets expire after ten minutes and share a 128 MiB byte budget plus a 256-item limit. Reads promote assets to most recently used; insertion evicts the oldest unused assets until both budgets fit. Consumers can request the page again if an asset expires or is evicted. Source and rendered-byte limits are operation/cache budgets, not supported-document page totals.

## Verification and documentation boundary

`packages/kap-server/test/workPresets.test.ts` covers the off gate, home isolation, explicit installation/retry, non-revival after disable/removal and a real PluginHost table comparison followed by an authorized report preview. Set `KIKI_WORK_PLUGIN_ROOT` to local package sources to include the real-tool integration test. `test/documentPreview.test.ts` covers bounded large-text ranges, UTF-8 continuation, browser PDF fallback, byte-budget asset eviction, session asset isolation, Office missing-dependency recovery and worksheet navigation. The plugin-state case in `test/documentPreview.integration.ts` verifies that fresh and disabled Office installations return distinct recovery states without auto-enabling. `apps/kimi-code/test/cli/serve-recovery.test.ts` covers live unreachable peers, pre-registration child PID leases, cancellation and lease retention when cleanup cannot be confirmed. GUI `connection.test.tsx` and `host/tauri.test.ts` cover passive progress, shared IPC results and cancellation followed by late results. Native tests in `src-tauri/src/lib.rs` cover discovery followers, PID lease transfer, cancellation and shutdown ownership. `packages/session-core/src/composer/media.test.ts` covers format classification. Native mode identity is covered by `work_mode::tests::modes_are_window_local_not_home_settings`.

The shared daemon has been exercised with two real WebSocket clients: concurrent ensure calls reused one server and closing either/both clients left it running. This does not prove the desktop two-space/four-window workflow or model-driven skill utility. Those remain separate integrated acceptance checks.

Documentation impact is Generated + Maintainer + User. Generated plugin manifests are synchronized with their definitions; protocol schemas are the canonical contract. This maintainer view is complete for owner handoff. User views `docs/en/features/spaces.md`, `docs/zh/features/spaces.md`, `docs/en/guides/interface.md`, `docs/zh/guides/interface.md`, and both `configuration/env-vars.md` pages are synchronized in this candidate. Their mode/window and canvas claims still require the integrated desktop/GUI acceptance described above before default-on or public release. Work semantics are Kiki-only; OfficeCLI/PDF.js/PapaParse rendering/parsing behavior is adapted from those dependencies. No public release or plugin catalog publication is implied by this candidate.

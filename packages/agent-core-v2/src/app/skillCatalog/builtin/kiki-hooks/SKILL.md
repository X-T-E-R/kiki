# 编写 Kiki Hooks

把用户想要的自动化做成可验证的规则，先分清是提醒、观察，还是执行脚本。

## 先选轨道

- **注入指导**：例如「每完成三步提醒主智能体核对证据」。用当前声明式规则，将短文本送到适合的时机。
- **观察事件**：例如「记录工具执行失败」。用当前声明式观察规则，只记录事件，不改变操作。
- **执行脚本**：例如「任务完成后运行我的通知脚本」。用明确标为旧版的脚本协议；它和前两类不是同一种格式。

从已有请求判断目标，只问缺少且会改变动作、作用范围或触发时机的内容。普通工具调用直接执行；定时发送消息交给原生调度，不用 hook 代替。

## 编写最小规则

先读本机安装的 hooks 文档，再按所选轨道用 Read 阅读 `references/authoring.md`；内置调用时，制作参考已附在下方。确认要给所有项目使用，还是只给当前项目使用，读取已有规则后保留无关内容。根据实际绑定选择主智能体或子智能体、模型或执行角色，不擅自把「提醒我」扩成所有智能体都收到。

指导文本写成一次能执行的短提醒；节拍按已完成的模型步骤计，不按工具数量计。观察规则不要承诺发通知、运行程序或拦截。脚本则按旧版协议处理输入、输出、退出状态与超时，复用用户已有程序和本机运行环境。

当前声明式规则引用的文件只能用相对路径，且不能离开所属目录范围；遇到不支持的路径，说明本机版本限制，不用链接或其他配置绕过。未来新版脚本动作尚未提供，不先生成无法加载的规则。

## 验证真正生效

1. 为规则准备一个会触发和一个不会触发的本地样例。涉及脚本时，先用样例输入检查输出和退出状态，不用真实外部发送测试代替本地检查。
2. 保存后调用原生 `hooks-inspect`，检查有效来源、是否激活、未启用原因、实际绑定和下次到期计数。根据具体诊断修复，不以「配置已写入」结束。
3. 在目标会话触发对应事件，再检查提醒是否送达或观察是否命中；节拍规则还要检查到期前不触发、不属于目标的智能体不收到。旧版脚本另查实际执行结果，声明式检查视图不能证明旧脚本运行成功。

默认沿用 Kiki 的信任与执行方式，不为 hooks 增设逐次审批或另造沙箱。安装与启用交给原生宿主处理；脚本会写文件或向外发送时，说明这一项实际影响即可。

## 交付

给出规则和必要脚本的位置、作用范围、触发时机，以及命中与不命中的验证结果。当前没有可调用的检查客户端时，保留本地验证结果，并明确尚未验证会话内生效，不编造新的 CLI 检查命令。

# Built-in tool workflows

Use this reference for the cases that require more than a single ordinary tool call. The current tool schema and actual result take precedence over examples here. The complete user-facing field reference is installed at `<KIKI_HOME>/docs/<locale>/reference/tools.md`.

## File inspection and editing

- A known text path goes directly to `Read`; do not first locate it with `Glob` or use `Bash` to `cat` it. Send independent file reads in parallel. `Read` is not a directory lister; use `Glob` to find filenames, `Grep` to find contents, and `ls` only when listing one known directory suffices.
- `Read` returns at most 1,000 lines or 100 KB; use `line_offset` (1-based; a negative offset counts from the end) and `n_lines` to page. The output prefixes each line with a line number and appends a `<system>` status block. Neither is source-file content. If a long line is truncated, narrow the request or use a targeted operation rather than copying the elided line. UTF-16 is transcoded for display, but `Write` and `Edit` still expect UTF-8 input; convert encoding deliberately first. Binary files and unsupported encodings are not text.
- For exact replacement, `Read` the target immediately before every `Edit`, remove the displayed line-number prefix, and copy `old_string` from that view. If several locations match, supply context or use `replace_all` only when every match should change. Re-read between sequential edits to the same file. Pure CRLF appears as LF to `Read` and stays CRLF after `Edit`; mixed line endings require the visible `\r` in the match. Avoid re-reading solely to prove an edit landed; verify the relevant external contract or result instead.
- Use `Write` for new files or complete replacements, not small edits. Read an existing target before overwriting it. Appending adds exactly the supplied bytes without a newline; large new content can be split into an overwrite followed by appends, but do not chunk-edit an existing file. Avoid unsolicited README or completion-summary files. Sensitive-file access, symlink targets, and external paths remain subject to approval even when a directory itself was trusted.
- `Grep` uses ripgrep regexes, not shell grep syntax: escape regex metacharacters when searching for literals. Hidden files are searched; ignored build files need `include_ignored=true` and sensitive files stay filtered. `Glob` returns files, not directories. A bare `*.ts` recurses, `src/*.ts` matches one level, `src/**/*.ts` reaches subdirectories, and brace globs like `*.{ts,tsx}` are accepted. To find a directory, match a file beneath it. Avoid broad `node_modules/**`, `.venv/**`, or build-output walks. Page with `offset` and `head_limit`; each page rescans, so concurrent changes can shift entries. A timeout or capture limit may make a result incomplete; narrow the search rather than assuming a later page will recover unseen matches.
- `ReadMediaFile` handles images and video, not text. After generating or editing media, read it back. The result gives original dimensions and delivery status. Calculate absolute coordinates from those original dimensions, not a downsampled display. If tiny text is blurred, use `region` with original-image pixel coordinates; re-reading unchanged without a crop reproduces the blur. `full_resolution` only fits within the model's payload limit. If compression cannot fit the media, create a smaller copy, then read that copy; do not retry the unchanged file.

## Shell and background work

- `Bash` is for shell semantics: pipes, scripts, git, package managers, builds, tests, and processes. A pure `cat`, `head`, `tail`, recursive filename search, grep, heredoc, or source-file redirection belongs to the dedicated file tool. The Bash result may append one brief hint for such a command; it does not block or rewrite execution. Tell the user something in your reply, not by running `echo` solely as a message.
- Shell calls start fresh: `cd` and shell variables do not persist. Supply `cwd` or an absolute path and quote paths with spaces. Chain dependent commands with `&&`, use `||` for fallback and `;` when independent sequential execution must continue after failure. Issue unrelated read-only checks in parallel. Never use Bash to bypass sensitive-file filtering or another tool's admission; avoid superuser commands, external-workspace changes without authorization, and indefinite interactive foreground work. Check an uncertain executable with `which`.
- Foreground commands default to 60 seconds and may move to background on timeout. An explicit background call requires `description`; it returns a task ID, not the command's final output. Use `lifetime=service` only for a server, watcher, or listener; a finite command has an execution deadline unless `disable_timeout` is deliberately set. Automatic completion normally delivers the result. `TaskList` rediscovers task IDs after compaction; `TaskOutput` provides a nonblocking snapshot and `output_path`. `TaskStop` cancels only work you own and can leave partial side effects. Do not stop work that is about to finish just to get its result.
- For an interactive main agent with automatic completion notification, continue other work or end the turn normally when none remains; ending the turn neither closes the session nor completes the task. Do not poll `TaskOutput`/`AgentList` or repeatedly call `TaskWait` to keep the turn open. `TaskWait` requires `timeout` 1–86400 seconds and accepts an optional `task_id`; without an ID it waits for any task running when the call starts. Outside active goal mode, main can wait for a running agent task only with `sync_wait=true`, a specific `task_id`, and a concrete non-empty `sync_reason` for a genuine same-turn dependency. Active goal and subagent waits do not require those exception fields. Steer input ends the wait early without stopping tasks. Timeout leaves tasks running; a terminal result delivered by `TaskWait` is not delivered again by automatic notification. A subagent must settle its own dependencies before returning a final receipt.
- `TaskList` defaults to active tasks; pass `active_only=false` to inspect terminal ones. Page using `next_offset` but expect roster shifts. Completed subagent results require a verified receipt; `legacy_unverified`, `invalid`, and `contentState: unavailable` are not complete reports. `TaskOutput` tail preview is bounded; for long logs use `output_path` with `Read`, or `offset`/`max_bytes` with byte-oriented `next_offset`. A shell failure uses a nonzero `exit_code`; `terminal_reason` distinguishes timeout, explicit stop, or an error with no ordinary exit code. An ordinary failure does not need a `stop_reason`.

## Delegation and collaboration

- Delegate coherent work when parallel progress or context isolation pays for handoff, not for a trivial one-file lookup. Brief a new subagent as if it has not seen this conversation: objective, exact paths and facts already known, authority, success evidence, and stop or handoff condition. Unknown file locations can themselves be its exploration question; do not prescribe investigative steps that assume the answer. Do not redo a live child's investigation. Resume the same child by name or ID for a follow-up or timeout; do not silently start over.
- `AgentRun` omitting `background` means background for main and foreground for subagents, including resume and goal mode. Set `background=false` explicitly for a genuine same-turn dependency. Main foreground waits detach on steer / Send now input without stopping the child, so the next safe step can read the input and completion still notifies automatically. If TaskList, TaskOutput, and TaskStop are unavailable, main omission and explicit `background=true` fail before launch; enable those tools or explicitly request synchronous execution, never assume a foreground fallback. `AgentRun` `description` is a short UI label. A new explicit `profile_file` is a role definition, not a shared prompt; it is mutually exclusive with `profile`, `route`, and `resume`. A stable `name` makes `AgentList`/`AgentSend`/resume easier. On resume, omit `profile`, `profile_file`, and `route`; omit `effort` to keep the saved setting, or set it for the next idle run. A different canonical model needs `allow_model_change=true`; caller lease, role, route, and executor restrictions still apply. Do not assume missing model/effort defaults inherit from the caller: request inheritance explicitly. A provider that cannot change an existing external thread binding returns an error rather than recreating it.
- A child report is visible to the parent, not automatically to the user. The parent integrates it and relays relevant evidence. A `running` child in `AgentList` may not have a tracked task or a pending completion notice; consult `TaskList` for tasks. `AgentList` lists only direct children; names must come from `AgentRun`, not guesses.
- `AgentSend` accepts an unambiguous direct-child `name` or `agent_id` and a self-contained nonempty message; the child does not see this conversation. The result often says queued because sending does not await consumption. A running native child receives it at a step boundary, a running external child on its next run, and an idle resumable child starts a background run. A full mailbox requires waiting for it to drain before retrying. A starting, cancelling, or no-longer-resumable child is not restarted. `AgentNotify` is for a genuinely new fact that makes the parent change course before the final result, not startup, routine progress, an ETA, or a copy of the receipt. It is one-way: delivery is not evidence of approval or reading. A blocked subagent near completion should report in its final receipt.
- `ThreadCreate` creates a separate user-owned top-level session only on the user's request; unlike `AgentRun`, its work does not return as this agent's result. `cwd` must exist and be absolute; omitted `cwd` uses the current workspace. `profile` selects an enabled main-agent profile; `model_alias`/`effort` must resolve for that main agent (no `inherit`). An initial permission mode cannot exceed your current effective mode, and `plan_mode` may set initial state. `prompt` becomes the new thread's first user message and starts it; without one it waits empty. Use `ThreadList` then `ThreadSend`/`ThreadWait` for further interaction if communication is enabled. Creation failure before prompt acceptance removes the new thread.
- Use `AskUserQuestion` only when the answer materially changes the next action; it provides 1–4 questions, each with 2–4 distinct choices and an automatic Other option. Keep labels brief and put tradeoffs in descriptions. Use `multi_select` for genuinely independent choices; the answers map is keyed by question text. An empty/dismissed result does not select the recommended option. A background answer must arrive before its dependent action. A plain question is enough for free-form input.

## Plan, goal, and schedule

- Enter Plan mode for consequential implementation with genuinely competing approaches or substantial uncertainty, not automatically for a multi-file change, a tiny fix, or pure reading. Once inside, follow the plan reminder: investigate, choose an approach, write the plan file, then use `ExitPlanMode`, which reads that file rather than taking its text as an argument. Name actual files, steps, and verifiable checks, not vague aims. Plan mode limits editing to the plan file; fresh native research children have a strict builtin read-only ceiling that persists after plan exit and resume. Existing background work continues, and the parent's Bash permissions are unchanged. It is not a sandbox. Do not use `AskUserQuestion` merely to ask whether the plan is acceptable; `ExitPlanMode` handles review. If rejected, revise the file. Offer `options` only for meaningful alternatives. Auto mode exits without asking; manual/yolo display the plan to the user.
- `TodoList` is a transient list owned by the calling agent, not the persistent task board and not another agent's list. Use for multi-step work, with one `in_progress` item while working; mark done only after implementation and relevant checks pass. Omit `todos` to query and pass `[]` to clear. Avoid churn when no status actually changed. In Plan mode the plan belongs in its plan file.
- `Cron` uses `action=create|list|delete`. Create requires local-time five-field `cron` and a `prompt` of at most 8 KiB. The default `recurring=true` repeats until deletion or seventh-day expiry; `false` fires at its next matching time and auto-deletes. Pin minute, hour, day, and month for one-shot dates; a pinned calendar date with `recurring=true` repeats yearly. List returns IDs and next times; delete by a listed ID is irreversible. Sessions retain schedules when unloaded, not in a brand-new session. For one-shot cron scheduled at `:00`/`:30` or recurring ticks, scheduler jitter can move the actual fire; missed firings coalesce on wake. A recurring job can fire one final time as stale before expiring; recreate if still wanted. `KIKI_DISABLE_CRON=1` disables firing and new schedules.
- `Goal` uses `action=create|get|set_budget|update`. Only create when the user explicitly requests an autonomous goal or host intake requests one. A verifiable objective names the finish line and evidence; include user-supplied completion criteria, explicit exclusions and stop conditions, without inventing requirements. If wording is genuinely ambiguous, settle it before creating. Do not replace an existing active/paused/blocked goal without user direction. Budget only when the user gives a clear turns/tokens/time bound; convert compound durations into one supported unit, and do not infer a limit from “be quick.” A time budget must be finite and at least one second; turns/tokens are positive integers. Use `get` for status. `update=active` resumes on user direction; `complete` only when the actual objective and validation pass. A useful partial slice needs no status call: the goal continues next turn. `blocked` means a genuine impasse, not just difficulty or remaining work. A nonterminal obstacle needs to persist for three consecutive goal turns; impossible or contradictory objectives can block immediately. Explain completion or blocker after setting status.
- `WebSearch` finds sources; a typed answer is provider synthesis rather than independent verification. `lane`, `lanes`, and `preset` are mutually exclusive; typed output requires a single lane. Invalid explicit selectors do not silently switch providers. Use `FetchURL` for the source's full text and cite actual URLs. Both tools default to synchronous calls; asynchronous calls require `idempotency_key` and return a donor job receipt, not a Kiki background task. Use the same tool with `get`, `read`, `cancel`; honor `poll_after_ms`, not a busy loop. `read` returns base64 chunks and byte offsets, not plain text; a successful job can contain only partial content. Preserve truncation and partial-result notices.
- `FetchURL` URL shorthand (`url`) and action/source form must not be mixed. Inline text/bytes and scoped local files cannot use egress pipelines. A file source needs a configured donor scope and relative path; admission binds the canonical path and file identity. In-place updates are read from the admitted object, but replacement changes its identity and needs a new approved call. A scope does not grant arbitrary host access or bypass sensitive-file rules. Unsupported mode/pipeline combinations fail rather than falling back. Authentication walls do not become authenticated page content.

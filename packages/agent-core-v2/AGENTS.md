# agent-core-v2 Agent Guide

> The sole agent engine, built on DI scopes and explicit runtime ownership. The historical `packages/agent-core` engine has been removed.

## Scopes

Three `LifecycleScope` tiers (`App` / `Session` / `Agent`) are declared in `src/app/scopes.ts`. The DI kernel only knows opaque `ScopeKind` strings and the topology installed by `setScopeTopology`.

Workspace ownership is separate from DI scope topology. App-scope `IWorkspaceInstanceManager` (`src/workspace/workspaceInstance/`) manages leased `WorkspaceInstance` objects, each holding a `RuntimeRegistry`, `RuntimeUnitHost`, and `Program`. `src/program/program.ts` owns runtime-generation resources: filesystem/watch/git, instructions, skill/profile discovery, MCP, and trust. Generations and workspace instances can retire and dispose; do not treat them as permanent App resources or reintroduce a Workspace DI tier.

The App-scope `ISessionManager` (`src/app/sessionManager/`) is the cross-workspace lifecycle facade. Each Program's session controller (`src/workspace/sessionLifecycle/sessionLifecycleService.ts`) creates Session scopes from the App instantiation service and supplies workspace-derived session seeds (`ISessionSkillCatalogData`, `ISessionInstructionsProvider`, `ISessionMcpHandle`, `ISessionWorkspaceInfo`, profile workspace key, and ephemeral MCP configuration). `configureContainer` anchors the session lock and workspace reference before activation, and fires `onWillCreateSession` with `readSeed` / `contributeSeed` / `onSessionDispose`. Preserve that ownership and release ordering when adding session resources.

Agent profile registration remains App-visible through `IAgentProfileRegistry`; each Session's `ISessionAgentProfileCatalog` owns the effective merged/scoped view. Use the effective catalog for execution decisions rather than an unfiltered list of registrations. Workspace MCP and trust services remain Program-owned; process-wide management and persistence stay in their App domains described below.

## Units and contribution points (L3)

The DI kernel (`src/_base/di/`) owns the unit layer on top of the scoped registry:

- `service.ts` — `Service`: the unit base class (extends `Disposable`). Capabilities live on `this` (`provide` / `effect` / `on` / `get` / `ref`, plus `name` / `state` / `config`). Two-phase construction: inside the ctor `provide`/`on`/`effect` buffer (writes only — `get`/`ref` throw, dependencies are constructor parameters); the kernel binds the runtime after `Reflect.construct` and flushes in writing order; a manually `new`ed instance throws on every capability call. Services whose own members collide with the `Service` vocabulary keep `extends Disposable` — still full DI units (cascade/ledger do not require `Service`).
- `fiber.ts` — the `Fiber` capability interface (not a DI token), `FiberHandle` (thenable / `state` / `uid` / `update` / `dispose`), `ServiceRecipe` (class / arrow function / `{apply}`), the `FiberState` five-state machine, and `ScopeUnits(kind)` — the materialization collection token, one per scope kind.
- `collection.ts` — `collection<T>(name)` contribution tokens. Contribute with `this.provide(token, value)`; a fold declares the token as a constructor parameter and receives a `CollectionView<T>` (`items` / `records` / incremental `onDidChange`). Records are visible to the provider's ancestors and descendants (never sibling subtrees); provider death withdraws. Collection edges enter the graph for introspection but never join a cascade contagion set.
- `scopeUnits.ts` — the kernel fold: every scope-creation point (`createScopedChildHandle` / `Scope.createApp` / `Scope.createChild`) runs `watchScopeUnits(container, kind)` before eager activation, materializing each visible `ScopeUnits(kind)` record's recipe as a unit inside the new scope (disposal hangs on the record provider's book — provider death tears the materialized units down across the tree). `ScopeOptions.configureContainer` runs at the same point (the session seed adapters use it).
- `instantiation.ts` — the `@ref(IX)` decorator factory (`LiveRef<T>`: `current` live read + `onDidChange` availability event; observation creates no binding and no graph edge) and `ScopeActivation`.
- `src/app/feature/` — `IFeatureManager` (App scope): runtime unit assembly (`provideUnit` / `unprovideUnit` / `updateUnit`) and introspection (`units()` / `onDidChangeUnits`); managed units hang on the manager's own book. External package management stays with `IPluginService`. The `features` assembly (`src/features/featureAssemblyService.ts`) drains the module-level feature table through it.

The four contribution seams (token → fold): config sections — `ConfigSectionContribution` → `ConfigRegistry` fold (`src/app/config/`; module-level `registerConfigSection` stays the static built-in channel drained at construction, a withdrawn runtime record unregisters the section while user TOML values survive); agent tools — `AgentToolContribution` → `AgentToolActivationService` fold (built-in records provided once at App scope by `builtinToolAssemblyService`; `registerAgentToolService` stays the static channel: Agent-scope DI `OnDemand` registration + module table); agent profiles — `AgentProfileContribution` → `IAgentProfileRegistry` fold (see Scopes); event/state vocabulary — `EventStateContribution` → `IEventDispatcher` fold (a record bundles `events`; `registerEvent2Class` stays the static channel drained at fold time, while `defineState(...).replayable(...)` keys are explicit owner-service contributions: each replayable key's owning service contributes it via `contributeState` at construction — Agent-scope owners are eager, the session-domain todo/cron keys bridge through `agentLifecycle.onWillCreate` before `restore()` while interaction is contributed directly by the lifecycle — and replaying a withdrawn domain's history lands on the unknown-type skip-and-count path). A fifth seam: executable commands — `CommandContribution` → `IAgentCommandService` fold (`src/agent/command/`; a contributed command runs engine-side — `run(ctx)` gets `ctx.get` resolving through the agent container, valid only during the synchronous part of `run`; name-level dedup, last record wins; surfaced over RPC as `agentCommandService.list` / `run`).

`src/features/` — built-in capabilities authored as self-contained Feature units (`plan` was the first, extracted from `agent/plan` + `agent/tools/plan`; `externalHooks` from `app/externalHooksRunner` + `session/externalHooks` + `agent/externalHooks`; Tower is fully retired except for historical `tower_mode` wire decoding in `src/wire/retiredTowerEvents.ts`). A `Feature` (`src/features/feature.ts`) is an App-scope unit recipe with a `static override readonly name` and `contribute*` helpers composing the seams: `contributeService(scope, id, ctor)` / `contributeAgentService` (per-scope materialization via `ScopeUnits` — provider death retracts everywhere, 连坐), `contributeTool` (per-agent `OnDemand` registration + the `AgentToolContribution` record), `contributeProfiles`, `contributeConfig`, `contributeCommand`, plus `onDispose`. Feature modules self-register at import (`registerFeature`, `src/features/featureRegistry.ts`); the App-scope `IFeatureAssemblyService` drains the table through `IFeatureManager.provideUnit`, so every feature is a named, introspectable, retractable managed unit. Built-in features keep user-facing static contracts — config sections, agent profiles, wire vocabulary — on the static import=register channels (the config/state manifest generators read static tables / call sites; wire records must stay replayable); the Feature unit carries the runtime capabilities (services, tools, commands). The string form of the unit `on(...)` capability (`this.on('turn.ended', …)`) is backed by the production `FiberEventResolver` registered in `src/app/event/fiberEventResolver.ts`, resolving against the scope's `IEventBus`.

## Ledger and cascade (L0/L2)

- `src/_base/lifecycle/` — the Ledger (L0): ordered, dual-track (sync / async disposable) effect bookkeeping with strict reverse-order serial teardown and reason passthrough (`'scope-close' | 'cascade' | 'unload'`). Scopes, containers, and units all anchor side effects here; `Disposable` / `DisposableStore` (`_base/di/lifecycle.ts`) delegate to it. `IInstantiationService.onWillDispose` fires synchronously after resolution is disabled but before teardown; external event bridges must stop there rather than wait behind asynchronous service disposal.
- `cascadeEngine.ts` — one engine per scope container with tree-wide orchestration (L2): `provide` / `unprovide` / `update` run as transactions (contagion set from the persistent dependency graph — instance edges may point child → parent across scopes → abort hook → global reverse-topo teardown → apply → waiting-area recheck to a fixpoint → history ring). Units are five-state (`Pending / Activating / Active / Unloading / Failed`): construction failure is sticky `Failed` (no auto-retry; `update()` reloads; resolving a Failed unit rethrows its error); units with unsatisfiable declared dependencies park in the waiting area and auto-activate when the deps arrive, across scopes. An `ondemand` unit counts as available — consumers pull it transitively at materialization.
- Static and dynamic share one provide path: scope creation (`createScopedChildHandle` / `Scope.createApp` / `Scope.createChild`) submits the kind's whole `registerScopedService` batch as ONE cascade transaction via `provideAll` — every token registers before the activation wave, so registration order never matters (untracked transitive `createInstance` resolutions succeed inside the batch). The static registry is unique per (scope, token): `registerScopedService` throws a `BugIndicatingError` on a duplicate registration at import time — token identity is the decorator object, so an aliased second registration blows up the same way — and intentional replacement goes through `overrideScopedService`, which throws when no registration exists. A seed occupying a token overrides the static registration. `activateScopeServices` is gone — eager activation failure is a sticky `Failed` unit, not a scope-creation error.

## Comment conventions

- **No comments.** The code is the source of truth; do not write file headers, section banners, or implementation narration. The one exception is JSDoc attached to exported symbols (it flows into the generated `.d.ts` and the consumers' IDE hover); keep it focused on the public contract.
- **Lint-suppression directives are the tooling exception.** `oxlint-disable` / `eslint-disable` comments are allowed where they suppress an active rule for a deliberate pattern (e.g. the Event2 class+payload-interface merging idiom). `@ts-expect-error`, `@ts-ignore`, and `ts-nocheck` stay banned — fix the underlying type problem instead; negative type-safety cases go into compiler-asserted fixtures.

## Telemetry

Business events go through `ITelemetryService.track2` — never the low-level `track`, which exists only for appender plumbing and tests. Every event must be registered in `src/app/telemetry/events.ts` (`telemetryEventDefinitions`) before it is emitted: define a properties interface and document every property, then register it one of two ways — the compiler rejects unregistered event names and any property mismatch at the call site.

- Events whose every emission path goes through an Agent-scoped `ITelemetryService` view use `defineAgentTelemetryEvent<P>({ owner, comment, properties })`. `agent_id` is ambient Agent identity — declared once as `AgentTelemetryEventContext`, composed into the wire schema, and bound at runtime by the Agent-scoped `ITelemetryService` view that `agentLifecycle` seeds. Keep it out of the payload interface and out of call sites.
- All other events use `defineTelemetryEvent<P>({ owner, comment, properties })`. This includes Session/App-level events and events with any non-Agent emission path (e.g. `image_compress`, which the kap-server prompt routes emit through a session-scoped view). Per-event agent identity outside the Agent scope (e.g. `subagent_created`, `cron_scheduled`) stays as explicit `agent_id` business properties.

- **Naming**: event names and property keys are snake_case (`tool_call`, `duration_ms`). Durations, counts, and sizes carry a unit suffix (`_ms` / `_count` / `_bytes`). Use specific names (`error_type`, not `error`).
- **Privacy**: never register user content, prompts, or file paths as properties.
- **Stability**: registered event names and property keys are wire data consumed by dashboards — treat renames as breaking changes.
- The registry is the single source of truth; `test/app/telemetry/events.test.ts` enforces the naming conventions.

## Persistence

Business domains **do not implement persistence themselves** — they depend on a Service that owns the access pattern. Business code expresses *what* to store or fetch, never *how*.

- Append-log → `IAppendLogStore`
- Atomic document → `IAtomicDocumentStore`
- Blob → `IBlobStore`
- Domain-specific query → a dedicated Store (e.g. `ISessionIndex`)

Business code must not `import 'node:fs'`, write SQL, hand-roll append-logs / atomic writes, or hold file handles. Generic Stores are named by **access pattern** (`IAppendLogStore`, `IAtomicDocumentStore`); only domain-unique Stores are named after the domain (`ISessionIndex`). See `.agents/skills/agent-core-dev/persistence.md` for the full layering rules and decision tree.

### Append commitment

`StorageError.details.committed` on an append says whether `writeFile` for that batch had started. It does not mean the batch is durable.

- `false`: `writeFile` had not started. On the file backend, `open` is retried at most 4 times, 10ms apart, and only before `writeFile`. `AppendLogStore` keeps the pending batch and schedules one microtask retry for `EBUSY`, `EPERM`, or `EACCES`, but not `ENOSPC`. A later explicit `flush`, a log read's flush, or `AgentLoopService.recoverPersistence` can retry any batch known not to have started after storage recovers. None spins.
- `true`: `writeFile` had started; zero, some, or all bytes may be present, and `sync` or `close` may have failed. Never replay the whole batch. `AppendLogStore` retains the encoded batch and its pre-append generation, offset, and up-to-4096-byte boundary. A flush or log read verifies that boundary and that the stored tail is an exact prefix of the retained batch, then appends only the missing suffix; a complete tail gets an empty durable append to retry sync. Only durable success clears the failure and publishes projections. A changed generation, boundary, or tail rejects with `storage.corrupted` and keeps admission blocked. Without a captured boundary, the original error remains blocked.
- any other value, including omission: the error does not say whether bytes were written. The store keeps one historical microtask retry. That retry can append the same batch twice. Do not treat this path as exactly-once.

A failed turn-end save stays failed until the same `TurnEnded` is durable. `Turn.result` rejects on that failure; the native `durableResult` resolves after the original save recovers. Native child tasks wait for that durable result, so successful recovery completes the original task and its notification without another model or tool call. Cancellation releases that task's waiter; later persistence recovery still saves the original execution result without starting new work. `AgentPromptService.enqueue` also settles its prompt only after the save is durable.

`recoverPersistence` starts with seven retries, delayed by 100ms, 500ms, 2s, 10s, 30s, 60s, and 5min. For `storage.disk_full`, `storage.io_failed`, and `storage.locked`, it then keeps one non-overlapping 5min retry scheduled until the original save succeeds or the loop is disposed. Other errors exhaust the seven-attempt timer. After the initial backoff, an actual successful `IAppendLogStore.onDidWrite` can bring recovery forward, at most once per 30s, replacing any slow timer. `storage.corrupted` disables that automatic write wakeup and slow retry; explicit recovery still validates the journal before proceeding. Disposal removes the subscription and timer. The next loop or prompt enqueue, explicit native resume, or message delivery also retries that same save. Resume still applies the original idle, ownership, binding, and idempotency checks after recovery. A persistent failure returns the save error instead of `already running`; failure-sensitive `settled` waiters reject rather than hanging message delivery. `AgentList` keeps the child visible as `persistence_failed` with the original execution outcome and storage error. Klient loop status preserves `finalizing`, `persistenceFailure`, and `lastTurnResult` as optional fields for older-server compatibility.

`GET /api/healthz` returns `{ ok: true }` and does not report this failure. `GET /api/desktop-lifecycle` can show the session in `work_pending`; `POST /api/desktop-lifecycle` drains and stops the service.

Wire transcript proofs rely on the single writer under the session lock and `AppendLogStore.sourceRevision`'s observed append chain; nothing on the session-open, page-read or seal path rereads the whole journal. Opening an epoch reads only the journal's last 4096 bytes as its base boundary. A previous trusted receipt carries the epoch forward when its size matches: a format-2 receipt must also match the SHA-256 of its stored tail bytes, a legacy format-1 receipt is accepted on size alone. Live proofs hash only the bytes appended since the base, check the base boundary, and compare them with the accepted records; a changed identity, size, mtime or ctime outside a successful append rejects the proof rather than rehashing. Without a file identity, or on cold segments, each proof rereads the appended region and boundary instead of continuing a cached hash. Sealing writes a format-2 receipt with `{ size, tailBytes, tailSha256 }` from that same bounded digest, and kap-server cold reads check only that tail. The legacy format-1 full-journal SHA-256 is still verified once per wire fingerprint. As a result, an external rewrite of bytes before the epoch base (or outside the stored tail of a cold sealed wire) is not detected. Export, repair and explicit checks that need whole-journal integrity must hash the journal on demand with `digestWireBytes`.

Replay checkpoint saves are separate from canonical append commitment. `IEventDispatcher.saveReplayCheckpoint()` returning `false` means a skipped save; `replayCheckpointSkipReason()` identifies `disposed`, `pending_events`, `state_changed`, `unavailable`, or `journal_changed`. Flush, journal-identity/digest, encoding, and atomic-document write failures reject with their phase and original cause. The session-level checkpoint save attempts every agent, logs individual failures and aggregates an incomplete result as `false`. Unload leaves that session resident when its checkpoint is incomplete without rejecting an unrelated resume; archive still drains canonical state before closing. Idle checkpoint scheduling retries an incomplete save up to three times at 100ms, 500ms, and 2000ms after the initial attempt, only while idle with no pending interaction. Exhaustion remains logged; checkpoint retries never replay model or tool work.

`IUsageFactStore` (`src/app/usageFacts/`, eager App scope) projects canonical append commits into `cache/usage-facts-v1` through `IAppendLogStore`. `IUsageReadModel` owns the typed SQLite view at `cache/usage-read-model-v2/index.sqlite`, isolated from the generic `IQueryStore`. A writer lease protects publication; followers read committed generations and reject writes. Facts, token-support-mask totals, source/hour/turn summaries and contiguous coverage publish in one FULL-synchronous transaction. The hourly summaries retain attribution, usage state, token-support mask, timestamp bounds and occurrence counts, with prices applied only at query time. A summary is used only at the source's current generation and ordinal, with safe integer tokens wholly inside the requested range and bucket; other sources use the original facts. Schema 2 remains readable and writable by the previous backend. Older databases backfill summaries in transactions of at most 32,768 facts and 128 sources, preserving ordinal progress across cancellation and restart. History continues those pages under its request signal, yielding between transactions; followers can read original facts while migration is incomplete. Completing a source's summaries advances the query revision. Journal import stages large envelopes across budgets and restarts; managed rewrites keep the previous generation visible until the replacement is complete. Occurrences retain separate ordinals, including equal values, genuine zero and explicit unknown usage. Paged reads freeze their ordinal watermark across appends and reject a replaced generation. A damaged journal invalidates its typed coverage before canonical recovery; derived failures never reject successful canonical writes. `checkpoint()` flushes the journal and checks its length and canonical generation under the source lock without reading fact rows. Reader cancellation leaves the writer alive; a dead worker is reopened on the next operation, and an uncertain publication is reconciled from persisted progress rather than blindly replayed. The npm and SEA builds supply `usage-read-model-worker.mjs`. Retained deleted/ephemeral ledgers remain canonical: their typed importer publishes only validated header/payload/commit transactions, and an interrupted transaction resumes from its saved offset. Old generic Usage collections and journals are retained for rollback; this store does not delete production caches.

SQLite query-store reads accept a request `AbortSignal`; pass it through point reads, query execution and ordered-column pages. The worker prepares its five fixed point-read and batch statements once per connection, reusing them after transaction rollback and SQLite index changes. Closing or replacing the connection discards those statements; failed initialization never publishes them. A dead worker is retired before a later operation opens another; a write interrupted by worker death has an unknown outcome and must be reconciled from persisted source/head rather than replayed automatically. `createStaging(source)` returns an owned staging/publication pair: retain it across budget pauses and dispose it when the build completes or is abandoned. SQLite persists the pair's owner and reclaims it only after the owner lease is released or its process dies; closing the store drains accepted work, waits for worker exit, and releases its staging leases.

## Background tasks

`AgentTaskService.reconcile` closes a restored ghost that is not already terminal. A process ghost, an agent ghost with no `agentId`, and an agent ghost whose session metadata has no matching outcome become `lost`. The outcome is the existing `agents[agentId]` record in session metadata, written by `mirrorAgentRun` when that run finishes. It is one registry entry, not a scan of the parent wire.

Adoption requires both `taskId` and `agentId`. `status: completed` with a non-empty `resultSummary` becomes a completed task and stores that summary. A blank summary becomes `failed` with the empty-receipt reason. `cancelled`, and `failed` with `error: terminated`, become `killed` with the stop reason cleared. Any other `failed` record keeps its `error` as the stop reason. A metadata record without `taskId` is not evidence: the same agent id can be reused for another run. A metadata read failure leaves the ghost `lost`. An already-terminal `lost` task is not rewritten. Reconcile does not call `readJournal`, does not read the old wire body, and does not call `execution.run`. A `subagent.completed` or `subagent.failed` row that exists only in the journal is not enough.

## MCP management plane

The App scope owns the process-wide MCP management surface, split across three domains: `mcpConfig` (`src/app/mcpConfig/` — the `[mcp]` config section, the layered mcp.json loader with per-entry origins, `IMcpConfigStore` as the single write point for the user-level `mcp.json`, `IMcpOAuthStore` credential persistence, and `IMcpOAuthService`, the process-wide OAuth orchestrator with credential events, single-flight refresh, and proactive refresh timers), `mcpRegistry` (`IMcpRegistryService` — the unified read view over the file layers and plugin manifests with `source`/`origin`/`mutable`; runtime-name collisions keep both entries, and runtime resolution ranks the file entry above plugin entries — a file entry wins by presence, even disabled, while a disabled plugin descriptor is treated as absent; a project layer joins the view only when the queried cwd itself is trusted, matching what the workspace runtime would load), and `mcpManagement` (`IMcpManagementService` — guarded CRUD (project-layer entries reject as read-only; plugin entries never block, so a user-level write may shadow a plugin), connection-test probes, the locator-addressed inspection/auth-status surface, and locator-addressed OAuth begin/complete/cancel/reset with ambiguity rejection plus an idle timeout that cancels abandoned flows). The engine services and the edge exposure (kap-server routes, klient facade) are ungated. On the Workspace side, `workspaceMcpConfig` merges the same sources (same file-over-plugin precedence), watches the files and plugin reloads, follows the store's `onDidWrite` for immediate management-plane reloads, and publishes fingerprint diffs that `workspaceMcp` applies to the handler-shared `McpConnectionManager` (tombstones for removals); `workspaceMcp` also subscribes the OAuth service's credential events to reconnect affected entries. Session overlays (`session/mcp`) keep caller-injected ephemeral servers session-local.

Name-collision precedence is a deliberate, documented divergence from v1: v1 ranks an enabled plugin above the file layers (#2858), v2 keeps its historical file-over-plugin order, and each engine's management guards follow its own winner — the same `mcp.json` plus plugin set can therefore resolve a collision differently per engine. Do not "re-align" one side without an explicit product decision.

## Session index

`ISessionIndex` (`src/app/sessionIndex/`, App scope) serves session list/resume reads over two paths: the authoritative directory scan (`sessionIndexSource`, always correct, linear) and the SQLite-backed derived read model (`IQueryStore` at `<home>/cache/query-store-sqlite-v1/index.sqlite`, ordered-column keyset pages in a worker), gated by the compatibility-named `persistence_minidb_readmodel` flag (default ON; roll back via `KIKI_EXPERIMENTAL_PERSISTENCE_MINIDB_READMODEL=false` or the `[experimental]` config section). The read model has an explicit lifecycle — `uninitialized → preparing → ready/degraded` via `prepare()`/`status()`. During initial preparation, reads answer from the authoritative store and fold the `ISessionIndexMirror` queue in for read-your-writes; the first list shares one single-flight authoritative scan with the initial projection. A degraded reader instead triggers single-flight recovery: retire and reopen the query-store reader, then publish a fresh projection generation. Each recovery round permits at most three automatic attempts; list/count report building until recovery completes, while point reads use authoritative metadata and propagate read/decode errors rather than reporting missing. Exhaustion stays visible in `status().reason` and starts a 60-second cooldown without another recovery timer. After that cooldown, a real `get`, `listRecent` or `count` request can start the next single-flight bounded round; the periodic reconciliation tick does not reset the budget. Authoritative metadata read/decode errors propagate without retiring the query-store reader or rebuilding its projection. `reprojectNow()` remains an explicit internal retry. The query-store is structural-only — text-index definitions are rejected at definition level, so session operations never touch the global full-text index (`<home>/search-index`, owned by kap-server's search surface). The App host filesystem watcher coalesces metadata changes by session on a fixed-start 1-second timer, with at most 16 sessions per batch and 1024 pending keys. Targeted batches run under the mirror lock; unchanged fingerprints produce no document-body reads or query-store writes. Directory changes and pending-key overflow request an inventory pass, after pending session batches. Continuous metadata events do not postpone the timer or invalidate batches because of unrelated mirror writes. Full reconciliation rejects superseded plans before commit and checks its retry cooldown before incrementing the request counter. A 10-minute timer checks the directory inventory; metadata fingerprints are reused for at most 30 minutes before a full pass repairs missed watch events, while `reconcileNow()` forces a fresh fingerprint pass for explicit drift checks.

Workspace registration (`IWorkspaceService.createOrTouch`) and lookup of an already registered workspace read the workspace catalog directly, without waiting for legacy discovery or the session index. Workspace listing owns the single-flight legacy discovery; discovery runs outside the mutation queue and merges into the latest catalog under the queue so concurrent registration and deletion are preserved.

## Cron scheduling

`ICronScheduler` (`src/app/cron/`, App scope) keeps the task roster in memory, reloads on `ICronTaskPersistence.onDidChange` or directory-watch changes, and sets a timeout for the next due task. `pollIntervalMs` now controls the full-inventory safety refresh (10 minutes by default), not the due-task wakeup; `0`/`null` and `manualTick` still disable automatic firing. The refresh is the fallback if a watcher misses changes, and one-shot tasks are reloaded from disk after firing so their durable deletion cancels subsequent wakeups.

## Conversation undo

`context.undo` is the only persisted undo fact. `contextMemory/conversationTime.ts` owns the conversation clock (`isUndoAnchor` — the single tick predicate used by `computeUndoCut`, the checkpoint folds, and the transcript reducer) and registers the undoable protocol (`registerUndoableProtocol`). A state key whose value must follow conversation undo (todo, plan, task-notification delivery, …) **MUST** chain `.undoable()` on its `defineState(...).replayable(...)` definition — never hand-roll the checkpoint/clear/rollback folds — so the dispatcher expands the protocol folds (undo anchors push a checkpoint, compaction/clear drop the markers, `context.undo` rolls back through inverse patches; a custom `onUndo` replaces the rollback, as the conversation history does) and the undo pipeline's pre-cut depth check sees the key (the dispatcher tracks patch history and checkpoint markers per state key). World-time state (turn counters, task registries, revision counters) must stay outside undoable keys.

Message rewrites carry an optional `replacementPrompt` on the same `context.undo` fact. Prepare identity, media, runtime binding and undo availability before committing; cut and replacement append fold together, including the accepted request receipt. Preserve the logical `userMessageId` while assigning a new request ID, and keep origin and content metadata opaque. This rewrites the logical history projection, not the original wire records. A matching retry replays its accepted receipt; a changed body needs a new request ID. Normal session close uses `drain(reason, 'preserve-pending')` to release local waiters without recording cancellation for unlaunched durable queue entries; explicit abort and deletion still cancel.

Live context and transcript replay revise a user message only when both its `id` and `providerMessageId` match. Native prompts that reuse an `id` remain separate undo anchors with their own prompt-owned injections.

Compaction resource-release failures are logged through `ILogService.error` as `failed to release compaction resources`; they do not replace the compaction failure or invalidate an already committed result. Persistence-blocked compaction retains its resources for recovery.

## Model-facing reminders

Two delivery paths only — never introduce a third (no deferred-delivery queues, no mid-step splice channels): reminders that restate current state (goal state, plan mode, date change, …) register a `contextInjector` provider (`register`) that reconciles at every step head (before the step's request is built) and re-emits after compaction or undo; reminders that report a one-off event (goal cancelled, AGENTS.md discovered, `/init` finished, …) append at the event point through `IAgentSystemReminderService.appendSystemReminder` with origin `{ kind: 'injection', variant: '<domain_fact>' }`, where the event point must itself be a safe position (a step/restore hook, an idle moment, or the loop-event fold's deferred append). `kind: 'injection'` is a lifecycle classification (hidden from the UI, not an undo anchor, dropped by compaction), not a provenance claim; prompt-owned attachments additionally carry `ownerPromptId` so undo treats them as part of their host prompt.

- [`docs/windows-process.md`](docs/windows-process.md) — Windows Bash Job ownership, cleanup failure/retry, and the single build-time helper consumed by source, SDK, npm and SEA entries. Keep precompiled cross-host packaging intact; no runtime compiler or taskkill fallback for owned trees.
- [`docs/di.md`](docs/di.md) — Read **before adding any business capability**: a scenario-driven walkthrough of the DI × Scope black box, from "add a global service" through dependency injection, scope selection, disposal, delayed/eager instantiation, `invokeFunction`, `createInstance`, child scopes, and cycles — introducing each concept only as the scenario needs it.
- [`docs/service-design.md`](docs/service-design.md) — Read **before designing a new Service**: first-principles rules for choosing a scope, splitting a domain Multi-Scope, picking a calling style (direct call vs event vs veto event vs hook), and directing dependencies — the design companion to `docs/di.md`.
- [`docs/flag.md`](docs/flag.md) — Read **before gating behavior behind a feature flag**: declaring a flag in its owning domain and registering it at import time via `registerFlagDefinition`, checking `IFlagService.enabled(id)`, wiring the `[experimental]` config section, or deciding whether a flag is App-scope vs. per-session.
- [`docs/errors.md`](docs/errors.md) — Read **before raising errors from a domain**: defining a co-located `XxxError`, registering a code in `ErrorCodes`/`ERROR_INFO`, translating external errors (provider/HTTP, fs, MCP) at the boundary, or (de)serializing errors across RPC/SDK with `toErrorPayload`/`fromErrorPayload`.
- [`docs/di-testing.md`](docs/di-testing.md) — Read **before writing or touching any DI/Scope test**: picking the right harness (`InstantiationService` vs `TestInstantiationService` vs `createScopedTestHost`), declaring deps with `@IService`, stubbing collaborators, and teardown via `DisposableStore`.
- [`docs/features.md`](docs/features.md) — Read **before adding or extracting a built-in feature** (`src/features/<name>/`): the `Feature` base class, the `contribute*` seams, the static-vs-feature channel rules, and the assembly/retraction lifecycle.
- [`docs/config-manifest.toml`](docs/config-manifest.toml) — Generated list of every registered config section, in the on-disk `config.toml` shape (owner, scope, defaults, env bindings, schema fields). Do not edit by hand; regenerate with `pnpm gen:config-manifest` after adding or removing a `registerConfigSection` call — `test/app/config/configManifest.test.ts` enforces freshness.
- [`docs/wire-manifest.d.ts`](docs/wire-manifest.d.ts) — Generated declaration file listing every durable wire record type (an `Event2` subclass with `static durable = true` + `static schema`) as a payload interface (folding states, blob codec owners, and owner file in the doc comment; payload fields in real TS type syntax), plus a `WirePayloadMap`. Do not edit by hand; regenerate with `pnpm gen:wire-manifest` after adding or removing a durable `Event2` class — `test/wire/wireManifest.test.ts` enforces freshness and checks the file parses.
- [`docs/state-manifest.d.ts`](docs/state-manifest.d.ts) — Generated declaration file listing every state key registered into `IAppStateService` / `IWorkspaceStateService` / `ISessionStateService` / `IAgentStateService`, as `AppStateSnapshot` / `WorkspaceStateSnapshot` / `SessionStateSnapshot` / `AgentStateSnapshot` interfaces (keys grouped by defining file), plus the `AppStateKey` / `WorkspaceStateKey` / `SessionStateKey` / `AgentStateKey` unions. Self-contained: every value type is expanded fully inline with each named type marked by a `/* TypeName — source/file.ts */` comment (recursion stops with a `recursive` marker) — no imports, no helper declarations. Do not edit by hand; regenerate with `pnpm gen:state-manifest` after adding or removing a `states.contributeState(...)` call or a `defineState(...).replayable(...)` key (the Agent section covers the replayable keys contributed by their owner services, with each replayable key's fold/durable/undoable info) — `test/state/stateManifest.test.ts` enforces freshness and checks the file parses.
